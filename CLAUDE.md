# A Bloo Bloo Stats: agent guide

Read before changing anything:
- [CONTEXT.md](CONTEXT.md) is the domain glossary. Use its terms exactly (Match, Appearance, Squad Member, Poll, Snapshot, Raw Payload, Season, ...) in code, UI copy and tests.
- [docs/adr/](docs/adr) holds decisions that are hard to reverse. Do not contradict one without writing a new ADR.
- Linear (team **CLUBS**, project "v1 — A Bloo Bloo Stats") is the source of truth for work. Each issue's acceptance criteria are end-to-end scenarios.

## Stack
- Cloudflare Workers on the **free plan**: watch CPU per request, D1 reads and writes, and subrequests.
- React Router v8 in framework mode (SSR) through `@cloudflare/vite-plugin`.
- Read bindings in loaders with `import { env } from "cloudflare:workers"`.
- D1 binding `DB`, accessed through Drizzle (`app/db/`). Edit `app/db/schema.ts`, run `pnpm db:generate` to write a migration to `migrations/`, then apply it with `pnpm db:migrate:local` (or `:remote`). Never hand-edit generated migrations.
- D1 caps bound parameters at 100 per statement and the free plan caps queries at 50 per invocation: write many rows with `bulkInsert` (`app/db/bulk.ts`), and batch writes with `db.batch`.
- The Poll stores a Raw Payload only when its hash changes, and derives Matches, Appearances, clubs, players and Snapshots from it in the same batch (`app/poll/record.ts`, `app/poll/ingest.ts`). Parsing EA's strings lives in `app/ea/parse.ts`. The Poll also records each new Season in `seasons` when the current-season leaderboard's `gamesPlayed` drops, starting at its first Match (the oldest of its `gamesPlayed` latest Competitive Matches, not the Poll that saw the drop) (`app/poll/seasons.ts`), and both clubs' Skill Ratings on each Match: within an hour of a new Match, or backfilled a few Opponents per Poll for older ones (`app/poll/rating-targets.ts`, `app/poll/ratings.ts`). EA's `clubs/overallStats` batches clubs only as a repeated `clubIds` parameter; comma-separated IDs get a 400.
- **The home relay polls EA (ADR 0007).** EA's Akamai now answers only a real, windowed Chrome, so production sets `EA_POLL_SOURCE` to `relay`: the cron skips the Poll, and `pnpm relay` on the Mac mini collects it through Chrome (`collectPoll` with a browser `EaFetcher`, `scripts/relay.ts`) and sends it to `POST /relay/poll` (`workers/relay-routes.ts`). That route records it with the same `recordPoll` and runs Milestone detection. `GET /relay/plan` gives the relay Our Club and the Opponents to rate, and the wire format is in `app/poll/relay.ts`. Both routes need the `RELAY_TOKEN` Worker secret (401 otherwise, 404 when it is unset); the relay reads it from a git-ignored `.relay.env`. `scripts/relay-install.sh` installs a LaunchAgent that keeps it running (logs in `.relay.log`). The `test` env keeps `worker`, so specs poll the fake EA from the cron; `runTestRelay()` (`e2e/support/relay.ts`) runs the relay against it with plain `fetch`.
- The Worker entry point, `workers/app.ts`, has the `fetch` handler (React Router) and the `scheduled` handler, `runScheduled` in `workers/scheduled.ts`: the Poll, then Milestone detection (`runMilestones`), then the "after a Session or Season ends" jobs (write-ups, then the Session posts, then the Season Review posts). Each job after the Poll never throws and never touches the Poll's record.
- Milestones (CLUBS-36) are detected after each Poll that stored new Matches or Snapshots (`app/milestones/record.ts`), from the pure rules in `app/stats/milestones.ts` (one typed config per kind: thresholds, headline, figure, plain sentence). Landmarks come from EA's career totals between two Snapshots, pinned to the Match that crossed them (or, for counts EA lacks such as Perfect ratings, from the recorded Appearances); feats, Streaks and records from the recorded Matches (CLUBS-63: a Rage Quit counts by result in a Streak, never in a scoreline record). The only rating feat is a Perfect rating (10.0, CLUBS-52). Each has a unique `dedupeKey`, so detection is idempotent; while the table is empty it backfills from every Match and Snapshot, and a kind with nothing stored yet keeps what it finds in older Matches, so a new kind backfills on its first run. To drop a kind, move it to `RETIRED_MILESTONE_KINDS` (queries never show those) and delete its rows in a migration. Their comments are a `milestone` write-up kind, one call per batch (a Poll's Milestones in one Session), drained before Session recaps.
- **Discord Session posts (CLUBS-39)** live in `app/discord/`: once a Session `isSessionOver`, `runSessionPosts` posts one embed (scorelines with headlines, top performer, the Session's Milestone headlines, the recap's first paragraph) to the `DISCORD_WEBHOOK_URL` webhook (a Worker secret; without it nothing is posted). It waits for the recap up to 3 Polls, then posts without; a failed call is retried on later Polls (a 429 after its `retry_after`), 3 attempts at most. `session_posts` keeps one row per Session so nothing posts twice; its first run records every already-ended Session as `skipped` (plus a `release-baseline` row), so past Sessions are never posted. All third-party and model text goes through `discordText` (Markdown, links and mentions escaped), and every post sends `allowed_mentions: { parse: [] }`. No AI label.
- **Season Reviews (CLUBS-45):** once the Poll detects a new Season, the previous one is finished (`finishedSeasons`). The `season-review` writer (`app/ai/writers/season-review.ts`, first in `WRITERS`) makes one call per finished Season (version never changes) for the intro, the outro and a citation per Award; Award winners are decided only by the rules in `app/stats/awards.ts`. Pieces are stored as `season-review` write-ups keyed `seasonReviewKey(n, "intro" | "outro" | "award/<id>")`. `runSeasonReviewPosts` (`app/discord/season-review.ts`, table `season_review_posts`) announces a review once its intro exists, with the first 3 Award winners and the link. The page `/seasons/:number/review` 404s until then. **Owner rule: nothing links to a Season Review** (no nav item, index, Analysis or Season-picker link); the Discord post is the only way in. No backfill: only Seasons that end from now on get one.
- **Write-ups (ADR 0006)** live in `app/ai/`: Claude writes Session recaps, Match reports and headlines, and the State of the club from `app/stats/` numbers, **only in the scheduled handler, never on a request**. `generate(ctx, task)` owns the model (`AI_MODEL` in `app/ai/config.ts`, with prices), prompt caching, structured output, input-hash idempotency, retries with backoff and storage (`ai_jobs`, `ai_writeups`); `drainQueue` runs a few per Poll. A new kind of write-up is an `AiWriter` (subjects with a version, and a task: prompt plus input builder) registered in `app/ai/run.ts`, and a display with `AiWriteup`. Pages read with `latestWriteup` / `latestWriteups` (`app/ai/writeups.ts`) and must never import `app/ai/client.ts`. Build inputs "as of" the subject's moment (e.g. `getSessionBrief`) so they never drift. Club and persona names are untrusted: pass them through `promptName` (`app/ai/sanitise.ts`), and validate replies strictly in the writer's `writeups` (exact fields, length caps). Anything that acts once a Session is over uses `isSessionOver` (`app/stats/sessions.ts`). Match headlines (`app/ai/writers/headline.ts`) come from the Session writer's call; the `headline` writer is the backlog for Matches reported without one, and cuts any headline to 80 characters.
- `ANTHROPIC_API_KEY` is a Worker secret in production, never in the repo. `pnpm dev` has no key, so its Polls skip write-ups; `pnpm dev:ai` opts in with the key from the shell or a git-ignored `.ai.env` (and spends real credit). **Never create `.dev.vars`**: it stops E2E passing its fake upstreams' URLs in.
- Tailwind v4.
- Biome handles lint and format; 2-space indent, double quotes.

## Testing (ADR 0004)
- **End-to-end tests come first.** Every acceptance criterion in a Linear issue becomes a Playwright spec in `e2e/`.
- **EA is never called in tests or CI.** Tests run against the fake EA upstream, which replays recorded Raw Payloads from `fixtures/ea/`.
- **Nor is Discord.** Session posts go to the fake Discord webhook (`e2e/fake-discord/`).
- **Neither is the Anthropic API.** Write-ups call the fake Anthropic upstream (`e2e/fake-anthropic/`) with a dummy key. Unscripted, it answers a structured-output request with JSON fitting the schema ("Fake recap (reply 1)."; one array item per `enum` value, so every Match gets a report).
- **Unit tests** (`*.test.ts` next to the code) cover only parsers and stat formulas.
- **CI must be green before merging:** typecheck, lint, unit and E2E. Git hooks (simple-git-hooks, installed by `pnpm install`) run on commit: a secret scan (secretlint; the repo is public), Biome, a migration drift check when `app/db/schema.ts` changes, and typecheck. On push they run lint and unit tests. Never bypass them with `--no-verify`; after merging `main` into a branch, re-run `pnpm typecheck` before pushing.
- **Harness:** import `test`/`expect` from `e2e/support/test.ts`. Each test starts with empty D1 tables and a reset fake EA. Fixtures: `triggerPoll()` runs the real scheduled handler (`triggerPoll(at)`, or `test.use({ pollAt })`, sets its scheduled time: the clock write-ups judge what is due by, e.g. a Coaching week's release); `fakeEa.addMatch(win())` (builders `win`/`loss`/`draw`/`dnf`/`friendly` in `e2e/support/match-builders.ts`), `fakeEa.setPayload(endpoint, body)`, `fakeEa.failNext(403)`, `fakeEa.timeoutNext()`, `fakeEa.requests()`; `fakeAnthropic.reply(content)` (text, or an object sent as JSON), `fakeAnthropic.failNext(500, { type, message, count })`, `fakeAnthropic.timeoutNext()`, `fakeAnthropic.requests()` (each with its parsed `body` and `raw` text); `fakeDiscord.failNext(429, { retryAfter, count })`, `fakeDiscord.requests()`; `triggerPollWithoutDiscord()` runs the scheduled handler as if the webhook secret were unset; `db.rows(table)` reads a table through the test-only `/__test/*` routes. The `test` env retries a failed write-up on the very next Poll (`AI_RETRY_BASE_MS` 0) and times calls out after 1.5 seconds. Shared Session seeding for write-up specs is in `e2e/support/writeups.ts`.
- **Ports are per checkout**, so worktrees can run `pnpm test:e2e` at the same time. `e2e/support/ports.ts` derives a stable app port, fake EA, fake Anthropic and fake Discord ports (four in a row, in 20000-29999) from the checkout's path; `E2E_PORT`, `FAKE_EA_PORT`, `FAKE_ANTHROPIC_PORT` and `FAKE_DISCORD_PORT` override them. The `test` Wrangler env has no `EA_BASE_URL`, `ANTHROPIC_BASE_URL` or `DISCORD_WEBHOOK_URL`: Playwright passes this run's fake upstream URLs (and a dummy `ANTHROPIC_API_KEY`) to `vite preview` (via `CLOUDFLARE_INCLUDE_PROCESS_ENV`, so a `.dev.vars` file would block it). Locally an already-running server is reused only when its health check (`/__test/health?ea=…&anthropic=…&discord=…`, `/__control/health?instance=…`) proves it is this checkout's; another worktree's answers 409 and the run fails rather than sharing it. Never import ports or URLs from anywhere but `ports.ts`.
- Data-only specs are named `*.api.spec.ts` and run once (project `api`); page specs run on `mobile` and `desktop`.
- `app/ea/` and `app/poll/` must also run under Node (ADR 0005): relative imports there use `.ts` extensions, and no Worker-only APIs outside `app/poll/record.ts` and `app/poll/run.ts`.

## Conventions
- Stat formulas and queries live in the shared `app/stats/` layer. Pages never write their own SQL or repeat a formula. Read [app/stats/README.md](app/stats/README.md) before building a page or adding a query. Every stats page parses a `StatsFilter` in its loader, passes it through `resolveStatsFilter` (which finds a selected Campaign's Matches), and mounts `FilterBar`.
- **Two-places rule:** anything used twice goes in a shared module (`app/components/`, `app/stats/`, `app/lib/`).
- The Clubs League rules (Points Targets, Promotion Series, Chances) live only in `app/stats/divisions.ts`, each value with its source and confidence. EA publishes none of them, so correct a number there, never in the Campaign engine (`app/stats/campaigns.ts`).
- Display times in Europe/London, through `~/lib/london-time`, in one convention (CLUBS-22):

  | Kind | Example | Use | Helper |
  |---|---|---|---|
  | Day | `Wed 14 Oct` | A date on its own: Last met, Tracking since, "as of", Matches day headings | `formatLondonDate` / `<LondonTime format="day">` |
  | Moment | `Wed 14 Oct, 22:54` | When a Match was played, wherever it is listed or titled | `formatLondonDateTime` / `<LondonTime format="moment">` |
  | Time | `22:54` | Only under a heading that already names the day | `formatLondonTime` / `<LondonTime format="time">` |
  | Short date | `14 Oct` | Only where space is tightest: chart axis labels and the FilterBar's date trigger (`5 Oct – 12 Oct`, via `formatCalendarRange`) | `formatLondonShortDate` |
  | Relative | `4 min ago` | Only how old our data is (`LastUpdatedBadge`), never when a Match was played | `formatRelativeTime` |

  Days and moments add the year only outside the current London year (`Tue 14 Oct 2025`). The clock is 24-hour. Render dates with `<LondonTime>` so they are a `<time dateTime>`.
- **Comparing periods (CLUBS-60, ADR 0008):** Analysis's "Compare to" (`?vs=`, `app/stats/period-compare.ts`) compares a date range with the same number of London calendar days just before it (`?vs=prev`), and a Season with another Season (`?vs=<n>`). A Campaign or "All dates" never compares, so the control hides. Never compare with a year earlier.
- **Date filtering (CLUBS-21):** every date filter goes through the shared `StatsFilter` / FilterBar date range, never a page-specific control.
  - **Options:** "All dates" (the default), the presets Last 7 days, Last 30 days and Last 12 months, and a custom range picked on the calendar, all in one `DateRangePicker` (CLUBS-33).
  - **Boundaries:** dates are Europe/London calendar days, inclusive at both ends.
  - **URL:** presets serialise as `?range=7d|30d|1y`, so shared links stay relative; custom ranges as `?from=YYYY-MM-DD&to=YYYY-MM-DD`.
  - **Bad input:** an invalid range falls back to "All".
- Every page must work at 375px wide with no horizontal page scroll, and use the extra width on desktop.

## Workflow
- One branch and one PR per Linear issue. Name the branch with the issue's `gitBranchName`, and put the issue ID (e.g. `CLUBS-9`) in the PR title.
- Before opening a PR: run the code-simplifier agent and then the code-reviewer agent over the diff.
- The orchestrator merges a PR once CI is green. Workers Builds then deploys `main`.

## Production
- The Worker serves https://clubs.marabine.co.uk, declared as a custom domain in `routes` in `wrangler.jsonc`. Keep it there: a deploy without it would detach the domain.
- Workers Builds runs `pnpm run deploy` on every push to `main`: build, then `wrangler d1 migrations apply DB --remote`, then `wrangler deploy`.
- **Migrations must be backward compatible.** They reach production D1 before the new code does, so the code that is still live (including its 5-minute Poll) must keep working against the migrated schema. Add columns as nullable or with defaults, and add tables freely. To rename or drop something, first ship code that no longer uses it, then remove it in a later PR.
- The site is private and never indexed: every Worker response gets `X-Robots-Tag: noindex, nofollow` (`workers/app.ts`), static assets get it from `public/_headers`, and `public/robots.txt` disallows everything except the link-preview bots (Discordbot, WhatsApp, facebookexternalhit, Twitterbot, Slackbot, TelegramBot).
- Link previews (CLUBS-38, ADR 0006): every route's `meta()` returns `pageMeta({ title, description, path })` from `~/lib/page-meta` (title, description, Open Graph and `twitter:card`); a route's meta replaces its parents', so never return a bare `{ title }`. Match, Session, Squad Member and Opponent text comes from `~/stats/link-preview`; descriptions stay under 200 characters. Absolute URLs come from `SITE_URL` in `~/lib/site`. `og:image` is always the static `public/og-card.png`: **no request-time image rendering**, which the free plan's CPU and Worker size limits rule out. Previews never label text as AI-written.

## Visual design
A TV sports-broadcast look: angled score bars, ticker strips and bold condensed numerals on blue-slate surfaces. The palette is inspired by the Seattle Sounders but uses none of their marks, and nothing is copied from Sky Sports or any other broadcaster. Dark is the only theme. See every component live at `/styleguide`.

### Fonts
From Google Fonts, loaded in `app/root.tsx`. **Sofia Sans Extra Condensed** (`font-display`, weights 600 to 800, 800 italic) is for numerals, team names, nav, headings and table headers, set in uppercase like broadcast graphics. **Sofia Sans** (`font-sans`, 400 to 700) is for running text, labels and table cells. Use `tabular` only where numbers line up in a column.

### Motifs
- Angled edges (`clip-slant*`) on score panels, tabs, badges and chips. Cards and tables keep square corners with a 2px top rule.
- A green slanted tab labels a strip (the ScoreBar's Match Type, the Ticker's "Latest").
- Our Club is always deep blue (`sound-900`); Opponents are `shale-800`.
- Compare's tale of the tape puts Squad Member A on the left on deep blue (`sound-900` plate, `sound-300` share bars) and B on the right on `rave` (text `shale-950`). Each stat's label is centred; the leader's figure is bold with a rave pointer and "(leads)" for screen readers.
- Compare's "Rise and fall together?" (CLUBS-66, the Rating link) sits under the chart and team record: two cards, "Straight up" (lead, `sound-900` with a rave rule) and "Beyond the team" (`shale-900`), each a slanted kicker `Tag`, the correlation as a big signed numeral beside its verdict in words, and "Small sample" under 15 Matches; then one sentence on whether it is them or the team, and "When A played below their average, B did too in X of Y" both ways. Under 8 rated Shared Matches it is an `EmptyState`. The Squad table's "Vs team" column (after Apps) is the same idea per Squad Member, signed with `formatSignedDecimal`.
- The crest appears only as the favicon (`assets/crest-96.png`, the whole crest, via `public/favicon.ico` and a `<link rel="icon">`), in the header lockup and in Our Club's panel on the hero `ScoreBar`. Both of those use `CrestMark`: `assets/crest-mark.png`, the crest cropped to the face (the only part that reads that small), at 40px on a green slanted tab. Opponents get their real crest from EA (CLUBS-72): the Poll stores each club's `crestAssetId` in `clubs`, `crestUrl` (`app/ea/crest.ts`) points at EA's CDN, and `ClubCrest` shows it at 48px on the hero, hiding itself if the image fails. Our Club always uses our own crest, never EA's. No placeholders: without a crest the name stands alone, and Squad Members have no avatar at all. E2E never fetches EA's CDN: the `eaCrests` fixture serves `e2e/support/fake-crest.png` (`eaCrests.fail()` makes them 404).
- Panels in a strip are cut apart by 4px slanted seams of page background, so the slants run parallel (the `ScoreBar`).
- A result shows as a word as well as a colour: the hero's outcome tab ("Win", "Loss") on an outcome-coloured rule along the foot of the score, or a W/D/L `OutcomeBadge` beside the score in compact rows. A Rage Quit adds a `RageQuitBadge` ("We rage quit" / "They rage quit", from `rageQuitLabel` in `~/stats/counted`) to the tab cluster; never write "DNF" in the UI. On the Match page's line-ups a player's row carries a rave "MOTM" marker, a small tilted `loss` card icon (named "Red card") when they were sent off (CLUBS-61, CLUBS-64) and a "Rage quit" `Tag`; on phones the rage quit tag drops under the name. `OUTCOME_FILL` holds each outcome's fill and text colour.
- A sideways scroller that clips content fades it out at that edge (`useScrollFade` from `~/lib/use-scroll-fade` plus the `scroll-fade` utility), so it reads as "scrolls" rather than "cut off". It is a mask, not a colour gradient. `FilterBar` and `DataTable` have it; a table fades only its end, so the pinned column stays crisp.
- Rows that link somewhere read as rows, not as blue link text: pass `rowHref` to `DataTable` (or use `useRowLink` and the `LINKED_ROW*` classes from `~/components` in a hand-built table). The row header holds the link in ink, the whole row is clickable, and hover lights the header's left edge in rave. Blue `sound-300` text is for links in running copy only.
- Motion is limited to the Ticker scroll, the loading shimmer and a StoryDeck card wiping in (and its smooth scroll), and all stop under `prefers-reduced-motion`.

### Components (`import { … } from "~/components"`)
Every component is presentational: it takes props and never fetches. Shared domain types (`Outcome`, `PositionGroup`, `MatchType`) live in `~/lib/domain`.
- `AppShell`: header with crest lockup and nav, optional `ticker` slot. ADR 0008 sets the tabs: Matches (the home page, `/`), Squad, Analysis (with Trends merged in by CLUBS-59; `/trends` redirects there), Milestones. Four fit a 375px phone. Opponents, Sessions and Compare are reached by links, never tabs, and a new page earns a tab only if it overlaps none of these. If the items overflow a 375px phone the nav is one row that scrolls sideways (CLUBS-36): its clipped edge fades (`scroll-fade`, as on the FilterBar) and the current page's item is scrolled into view, so it never wraps or scrolls the page. Milestones goes last, the lowest-traffic item. `root.tsx` already wraps every route in it.
- `PageHeader` / `SectionHeading`: the page's single h1 (with an optional `aside`, e.g. a badge) and section h2s.
- `ScoreBar`: the broadcast score strip, on a `shale-800` score block with a slanted divider between the numerals. Use `size="hero"` for the lead Match and `compact` in lists; mark Our Club with `isOurClub`. The hero is capped at `HERO_WIDTH` (60rem) and centred; each side's mark, name and `detail` line (e.g. its Skill Rating) sit centred in its panel, short names set larger so they fill it, long ones wrapping to two lines and then clamping (the full name is the panel's `title`). Above it, `label` and `meta` form one slanted tab cluster (`PLAYOFF | FULL TIME | Sat 17 Oct, 22:49`); below it, `stats` is a three-figure strip (ours left, theirs right) that stacks label-over-values on phones. Both names are `ink`: the panel colour alone tells the sides apart. Use `MatchScoreBar` for a Match: it fills the cluster, the Skill Ratings and the strip (Shots, Pass %, Tackles, from `summariseMatchSides`, hidden unless both clubs have Appearances).
- `MilestoneCard` / `MilestoneList`: one Milestone with its figure as a scoreboard numeral, a slanted badge for its kind (rave for a Squad Member; for Our Club a `sound-700` "Club …" badge, a `sound-300` rule and the figure on a slanted `sound-900` panel, since the score strip already uses club blue), the headline, its comment, a "Since records began" tag on records, then the Match as a compact `MatchScoreBar` with Session and profile links. `showMatch` / `showProfile` drop what the page already shows.
- `MilestoneRow`: a Milestone without its Match, as a compact row with a left rule in its subject's colour (rave, or `sound-300` for Our Club) and a profile link. The Milestones page (CLUBS-51) groups Milestones by Session and then by Match: each Match's compact `MatchScoreBar` once (sticky beside its rows from `lg`), its `MilestoneRow`s under it, filtered by `?type=landmark|feat|streak|record` and `?who=`.
- `ClubLeaders`: the Milestones page's hero (CLUBS-51), one board per stat from `getClubLeaders`: a green slanted stat tab, the leader's figure as a scoreboard numeral over their name, the next two below (from `sm`; phones show the leader only). ### Charts
One approach on every page: **hand-rolled SVG and HTML in `app/components/charts/`, with no chart library**. That keeps the Worker bundle small and renders on the server. Follow the dataviz skill's rules:
- Series colours come from `SERIES_COLORS` in fixed order and are never cycled. Four series at most; past that, fold the rest into "Other" or use small multiples. The order was checked with the dataviz CVD validator against `shale-900`.
- `StepChart` puts ordered level names on the y-axis and marks moves up and down with triangles (`win` up, `loss` down), keyed in words below the plot. It is static, so it has no tooltip; a screen-reader table carries every point.
- Use a single y-axis and never dual axes. Lines are 2px, markers 8px with a 2px surface ring, bars at most 16px thick, gridlines 1px `shale-700`.
- Charts with two or more series get a `ChartLegend`. Text uses ink tokens, never the series colour.
- A series takes its place's colour unless it sets `color` (a `SERIES_COLORS` entry) to pair series up: Compare draws Squad Member A in series-2 blue and B in series-1 green, each 5-Match average `dashed`. Legend entries take the same `color` / `dashed`.
- `LineChart` takes an optional `reference` level (a 1px dashed `ink-muted` line labelled at the left, e.g. 50% on a Win % chart), which the y-axis always includes.
- `LineChart` has a snapping crosshair and tooltip (pointer, touch, and arrow keys as a slider) plus a screen-reader data table. `BarChart` labels every bar, so it has no tooltip. Use horizontal bars for rankings, because they fit phones.
- Category x-axes (`LineChart`, `StackedColumnChart`) pick labels with `axisLabelIndices`: a run of equal labels (several Matches on one date) is labelled once, and labels never crowd each other or the last one. The y-axis gutter grows to fit its tick labels; pass `integerTicks` for values that are never fractional.
- Format numbers with `~/lib/number-format` (`formatDecimal`, `formatPercentage`, `formatOptional`, `NO_VALUE`), never a local `toFixed`.
- Charts measure their container (`useElementWidth`), so they fit any width without scaling text.

### Do
- Design at 375px first, then use the width at 1440px (`lg:grid-cols-2`, four-up `StatGrid`). On a phone a page's main content (e.g. the Squad table) starts on the first screen: summary tiles above it go compact below `sm`.
- Put wide content in its own scroll container (`DataTable` already does). The page itself must never scroll sideways.
- Keep the copy in sentence case, using CONTEXT.md terms ("Squad Member", "Match").

### Don't
- Add hex values or Tailwind default colours in components; add a token instead.
- Use colour alone for meaning. Outcomes carry letters and stale data carries the word "Stale".
- Add a chart library, a second display font, gradients or drop shadows on cards.
- Use Sounders or Sky marks, logos or exact colour schemes.
